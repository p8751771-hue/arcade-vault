# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Arcade Vault is a platform for playing games online and competing for the highest score. The visual MVP is built (spec `01-mvp-pantallas-visuales`): five screens with mocked data and no playable games, plus the "Inicio" landing (spec `02-landing-home`) and the "Acerca de" page with a contact form that really sends email through Resend (spec `03-acerca-de-contacto`; the only server code so far). Spec `04-paleta-tv-antigua` replaced the neon theme with an old-TV palette on every screen, and spec `05-historia-arcade` added the "Historia" page (first arcades 1971–1982, sourced and cited in APA) and removed medal colors from the rankings. Spec `06-supabase-conexion` connected the app to an existing Supabase project (clients only: no tables, no auth, nothing visible changed). Spec `07-juego-asteroides` made the first game playable: it replaced the simulated `asteroids` with `asteroides` (id and title `ASTEROIDES`) running on a minimal canvas engine; the other five games are still placeholders. Spec `08-pantalla-completa` added a fullscreen mode (button and F key, with Wake Lock) to the game screen, for playing on a TV; spec `09-campo-panoramico` widened Asteroides' playfield to the screen's aspect in fullscreen. Spec `10-iman-crt` added the "imán" (magnet) easter egg: over the game screen the mouse pointer is a magnet and a left click distorts the screen like a CRT for 10 s, then a cited scientific dialog opens. Spec `11-leaderboard-y-tabla-de-juegos` created the `games` and `scores` tables in Supabase and removed every local game / score dataset: the catalog and the rankings are read from the database (only `asteroides` exists; the five placeholder games are gone from the app) and the game-over modal saves the real score with a player name. Real auth (`scores.user_id` exists but is always null) and the other five games are future specs; build them through the spec-driven workflow below. Talk to the user in Spanish.

## Spec Driven Design workflow

Features are developed with two project skills from https://github.com/Klerith/fernando-skills, installed with `npx skills@latest add Klerith/fernando-skills` (as the README says). The files live in `.agents/skills/` (shared with other agents) and `.claude/skills/` holds symlinks to them; `skills-lock.json` pins commit `0c33d2f` with content hashes. Edit the files under `.agents/skills/`, not the symlinks. Re-running the install command pulls the latest upstream version, so review the diff before updating:

1. `/spec <one-sentence feature description>`: asks clarifying questions, then writes `specs/NN-slug.md` with status `Draft` (or `Borrador`), based on `.agents/skills/spec/template.md`. It never writes code. It also seeds `specs/.spec-config.yml` if that file is missing.
2. A human re-reads the spec and changes its status to `Approved` (or `Aprobado`). The agent never does this.
3. `/spec-impl NN-slug`: refuses anything that isn't Approved. It works on the `spec-NN-slug` branch and implements the plan one step at a time, pausing for diff review after each step.

Both skills are user-invoked only (`disable-model-invocation`). Settings in `specs/.spec-config.yml`:

- `AutoCreateBranch` (default `true`): when `true`, `/spec-impl` creates the branch without asking.
- `AutoCommitSteps` (default `false`): when `true`, `/spec-impl` commits each step as `spec-NN-step-MM`. Nothing is ever pushed.

Implement what the approved spec says. Changes go into the spec first, and out-of-scope requests go into a future spec.

## Architecture

App Router project. Routes live under `app/`, shared UI in `components/` and data/logic in `lib/`; the `@/*` path alias maps to the repo root.

- `app/(site)/` is a route group whose `layout.tsx` is the `home-about` shell: a `min-h-screen` flex column with `SiteHeader` (wrapped in `<Suspense>` because `usePathname()` suspends on params outside `generateStaticParams`; its fallback mimics the 70 px bar), the page in a `flex-1` wrapper, and the global footer ("© 2026 ARCADE VAULT · HECHO CON PIXELES Y SCANLINES · v2.6.0"; "NEÓN" until spec 04), so the footer sits at the bottom of short pages. `/juegos/[id]/jugar` lives outside it on purpose (no header, no footer).
- `components/site-header.tsx` follows `references/home-about/nav.jsx` / `.av-nav`: icon logo + "ARCADE VAULT", links Inicio / Biblioteca / Salón de la Fama / Acerca de / Historia (pixel 9 px, black 2 px underline on the active one, inverted on hover; Biblioteca is also active on `/juegos/*`), decorative "CRÉDITOS · 03", and a `.btn-cut` "Iniciar Sesión" link, or a `.btn-cut-ghost` "{NAME} ▾" button that signs out. At ≤ 840 px the links and credits hide and a ghost "≡" opens the side panel (`#mobile-menu`, `inert` when closed, closes on backdrop click and on navigation). Its CSS is the reference's literally, so the logo and button wrap when space runs out (at 1280 they do, ~85 px tall, as in the prototype; one line at 1600); the one agreed deviation is a 12 px gap on mobile so it fits at 390.
- **Games and scores come from Supabase (spec 11).** Tables (`supabase/migrations/20261127000000_games_y_scores.sql`, types in `lib/supabase/database.types.ts`, generated with the Supabase MCP: regenerate when the schema changes), both with RLS on:
  - `games` (`id` text PK = the `GameId`, `title`, `category` with a CHECK of the 4 categories, `description`, `long_description`, `controls`, `created_at`): public read only, no write policy (read-only from the app; the one row, `asteroides`, was inserted by the migration). To add a game: a new row **and** an entry in `ARCADE_GAMES` (without the entry the cabin shows the placeholder and nothing is saved) **and** a cover branch in `components/game-cover.tsx` (an id without one draws a neutral background).
  - `scores` (`id` uuid, `game_id` → `games.id`, `player_name` 1–14 chars, `score` integer 0–99 999 999, `user_id` nullable → `auth.users`, `created_at`): public read and public insert (`with check (user_id is null)`), no update or delete. The CHECKs validate the format, **not** that the game was really played: anyone with the public key can insert a made-up score (known and accepted; anti-cheat is a future spec). Windowed and fullscreen scores are mixed (the mode is not stored).
  - **Files:** `lib/games.ts` and `lib/scores.ts` are client-safe (types, `CATEGORY_FILTERS`, `MEDALS`, `formatScore` / `formatDate`; `GameId` is now `string`). The queries are in `lib/games-data.ts` (`getGames`, `getGame`) and `lib/scores-data.ts` (`getTopScores(gameId | null, limit = 10)`, `getBestScore`): server only (they use `lib/supabase/server.ts`), they throw an `Error` if Supabase fails. Order: score desc, then `created_at` asc (ties go to who got there first).
  - **Pages** read them inside `<Suspense>` (`cacheComponents`) with `components/data-states.tsx` (`Loading`, `LoadError`, `EmptyRanking`; the `bare` prop drops the frame inside another panel). Every `catch` around a read starts with `unstable_rethrow(error)`, otherwise it swallows Next's prerender rejection of `cookies()` and logs a false error at build. If the database fails the screen says "NO SE PUDO CARGAR"; if there are no scores, "SÉ EL PRIMERO EN ENTRAR AL SALÓN DE LA FAMA". There is never fallback data. Rankings are not cached (a new score must show on reload).
  - **Dummy vs real:** the landing's `ACTIVITY`, `TOP_PLAYERS` and `STATS` in `lib/home.ts` are still invented example data (each activity row carries its game title as text, no longer a `GameId`). Test rows written to `scores` use the player name `USUARIO-TEST` and only that name, so they are easy to tell from the dummy data in the frontend.
- `lib/home.ts`: static, typed landing data (`FEATURES`, `STATS`, `ACTIVITY`, `TOP_PLAYERS`, `PLAN`, `FAQS`) copied from `home.jsx`; activity rows carry the game title as text (spec 11). `formatHomeScore` uses `es-ES` like the reference (`7820`, `184.220`), unlike `formatScore` (`de-DE`). No `Date.now()`, no database reads.
- `components/home/`: landing pieces (`Reveal` is also used by "Acerca de"; it takes `as="section" | "div"`). Server components by default (`floating-silhouettes`, `section-head`, `feature-card`, `mini-card`, `activity-ticker`, `top-players`, `accent.ts`); client ones only where needed: `reveal` (scroll reveal) and `hero-ctas` / `plan-cta` (read `useSession`: "CREAR CUENTA"/"EMPEZAR GRATIS →" become "VER MI RANKING"/"IR A JUGAR →" when signed in).
- `lib/api.ts`: `login` / `register` are still network-free stubs (the single place to swap in real auth); `submitScore(gameId, name, score)` (spec 11) inserts into `scores` with the browser client and throws if Supabase rejects it or does not answer.
- `lib/player-name.ts` (spec 11): `av_player_name` in `localStorage` (not `av_user`: the remembered name belongs to the device, the simulated session will disappear with real auth), `normalizePlayerName` (uppercase, max 14), `readPlayerName` / `savePlayerName` (both tolerate a missing or blocked `localStorage`).
- `lib/history.ts` (spec 05): `MILESTONES` (8, chronological; `creators` verified in the sources, empty in 1982), `HISTORY_SOURCES` (APA 7 data: `authors`, `year` or `null` → "s.f.", `title`, `container`, `url`), `SORTED_SOURCES` (alphabetical by first author ignoring a leading "The"), `STYLE_NOTE`, `formatApaCitation` / `formatApaReference` (they add the APA letter suffix, e.g. `2021a` / `s.f.-b`, when an author has several works in the same year; `formatApaReference` returns parts so the title can be italic). Milestone texts are Spanish **paraphrases**, never copies: no 8 consecutive words in common with the downloaded source text, and every milestone cites ≥ 2 sources. Sources must be reachable by automated clients (Britannica, the MIT Press Reader and `worldvideogamehalloffame.org` pages were rejected for 403/404; the Hall of Fame pages live at `museumofplay.org/games/<slug>/`); Smithsonian Magazine blocks `HEAD` but answers `GET`. `components/history/`: `milestone-body` (shared, hook-free: title · maker, "CREADO POR", text and linked in-text citations) and `coin-cabinet` (client: "INSERTAR MONEDA" / "CANAL ANTERIOR", → / Enter / ← while focus is inside, "CRÉDITO n/8", "VOLVER A 1971", 250 ms channel-noise overlay skipped with `prefers-reduced-motion`, `aria-live="polite"`; no saved position, no attract mode). `public/historia/estilo-neon.png` / `estilo-tv.png`: 1280×900 screenshots of the landing before spec 04 (commit `67565ac`) and after, taken with the Next dev indicator hidden and quantized to 256 colors (≤ 400 KB).
- `lib/about.ts`: static "Acerca de" data (`ABOUT_MISSION`, `HIGHLIGHTS`, `CONTACT_TIPS`) copied from `about.jsx`. `components/about/`: `highlight-icon` (server, the 3 pixel SVGs) and `contact-form` (client: shake on empty fields like the reference, then `fetch("/api/contact")` with a 15 s `AbortSignal.timeout` and the state `"▶  TRANSMITIENDO…"`). The result is NOT the reference's "VAULT-OS // TERMINAL" (replaced in spec 03's amendment because it read as developer jargon) but a result card in plain language: icon, title, sentence, a small `Código: CONTACT-…` line and a button. Tones: green ✓ success ("ENVIAR OTRO MENSAJE" empties the form), yellow ! for data the visitor fixes (`empty`, `email`, `too_long` → "CORREGIR DATOS") and red ✕ for failed sends (`rate_limited`, `unavailable`, client-side `network` and `unexpected` → "REINTENTAR"); both keep the fields. Texts and codes live in `ERRORS` and must match the table in spec 03. Press Start 2P has no uppercase Ó/É, so titles like "SIN CONEXIÓN" show a lowercase-looking accent (same as "CRÉDITOS" in the reference). The form sets `text-[14px]` because the reference body is 14 px.
- `lib/contact.ts`: contact API logic, imported only by `app/api/contact/route.ts` (the client imports types only). `ContactError` + `CONTACT_STATUS` (one code per cause and its HTTP status), `parseContactRequest` (returns `bad_request` / `empty` / `email` / `too_long`; max 60 / 254 / 2000 chars), `escapeHtml` and `sendContactEmail` (Resend SDK, `from: "onboarding@resend.dev"`, `to: CONTACT_TO_EMAIL`, `replyTo` = visitor, subject `[Arcade Vault] Mensaje de {name}`, escaped `html`; Resend's `rate_limit_exceeded` → `rate_limited`, any other Resend error, exception or missing variable → `unavailable`). Errors are logged with `console.error` without the key or the message content. No honeypot, rate limit or CAPTCHA (decided in spec 03).
- Environment: `RESEND_API_KEY` and `CONTACT_TO_EMAIL` in `.env` (git-ignored; `.env.example` is versioned with empty values via `!.env.example` in `.gitignore`). Resend's free plan without a verified domain only delivers to the email of the account that owns the key, so `CONTACT_TO_EMAIL` must be that address; otherwise the API returns `500 { error: "unavailable" }` (the cause is in the server log). Missing variables also return `500 { error: "unavailable" }` at request time; the build does not need them.
- `lib/supabase/` (spec 06): connection to the existing Supabase project (since spec 11 the games / scores reads and the score insert use it; both clients are typed with `Database`). `client.ts` (`createClient()`, `createBrowserClient` from `@supabase/ssr`, only for `"use client"` components) and `server.ts` (`async createClient()`, `createServerClient` with `await cookies()` and `getAll` / `setAll`; `setAll` swallows the error because Server Components cannot write cookies; only for Server Components and Route Handlers, and with `cacheComponents` inside `<Suspense>` when called from a page). Both create one client per call (never a module-level variable) and throw an `Error` naming the missing variable when called, not on import, so the build does not need them. Variables: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` in `.env` (empty in `.env.example`); the value is the `anon` / publishable key, never `service_role`. They are read literally (`process.env.NEXT_PUBLIC_…`) and inlined in the browser bundle at build time, so restart `next dev` or rebuild after editing `.env`. Packages: `@supabase/supabase-js` and `@supabase/ssr` (cookie API is `getAll` / `setAll`, not the old `get` / `set` / `remove`). Not done yet (future specs): Supabase Auth replacing `useSession` / `lib/api.ts`, session refresh in `proxy.ts`, saving contact messages.
- `components/session-provider.tsx`: mocked session (`useSession`) persisted in `localStorage["av_user"]`; works without `localStorage` (memory fallback). Names are uppercased and capped at 14 chars.
- Screens' client components: `site-header`, `game-library` (search + chips), `game-card` (a single `<Link>` with tilt that checks `prefers-reduced-motion`), `game-cover` (canvas port of `cover()`, 96×56), `hall-of-fame`, `auth-form`, `play-screen` (`PlayPhase` / `SaveState`; the "SIMULAR FIN DE PARTIDA" button only exists when `NODE_ENV !== "production"`).
- **Saving a score (spec 11)** happens in the game-over modal of `play-screen.tsx`: a "TU NOMBRE" text field (uppercase, max 14; prefilled with `av_player_name`, else the simulated session's name, else empty; the button is disabled while it is empty; Enter submits) and "GUARDAR PUNTUACIÓN", which calls `submitScore` with the real final score. States `idle` → `saving` → `typing` → `done`, or `error` (red-bordered notice, name kept, button "REINTENTAR", `av_player_name` not written). Only a game with an entry in `ARCADE_GAMES` writes to the database: the "SIMULAR FIN DE PARTIDA" of a placeholder (2500 points) never does. Guards: `saving` ref (no double submit) and `saveRun` counter (a response that arrives after "JUGAR DE NUEVO" is discarded). A retry after a lost response can duplicate a row (no per-run key; accepted). The `P` / `F` shortcuts ignore key presses whose target is an `<input>`, otherwise typing a name would pause or toggle fullscreen. Playwright MCP note: its browser only allows `localhost:3000`, so the browser-side insert to `supabase.co` is blocked (`ERR_BLOCKED_BY_CLIENT`); verify the UI flow with `page.route` fulfilling the request and the real insert with `supabase-js` from Node.
- `lib/arcade/` (spec 07): canvas games. Each game lives alone and the route and the engine know none of them:
  - `engine.ts`: generic `startGame(factory, canvas, handlers)`: `requestAnimationFrame` loop with `dt` capped at 0.05 s, keyboard (W A S D alias the arrows; `preventDefault` only while the game runs, so the game-over modal and the buttons keep working with the keyboard), pause and `destroy()`. It also hands each game the site font read from the `--font-press-start` CSS variable (`GameContext.font`).
  - `asteroides.ts`: Asteroides, ported from `references/games.js` (rules kept, neon drawing replaced by black strokes on `#6e8677`; rock size shown by stroke width 3 / 2 / 1.5 px). It draws its **own HUD inside the canvas** (score, `NIVEL n`, one small ship per life) and the React HUD in the cabin stays too: both show the same values.
  - `index.ts`: `ARCADE_GAMES`, the only place that maps a `GameId` to a game. A game becomes playable by being added there; `play-screen.tsx` never names a game.
  - **Wide playfield (spec 09):** the logical field is always 480 high (`FIELD_HEIGHT`); its width is `clamp(round(480 × screen aspect), 480, 853)` (`FIELD_MIN_WIDTH` / `FIELD_MAX_WIDTH`), so 16:9 gives 853, 5:4 gives 600, 21:9 stays at 853 with side stripes and a portrait window gives 480. The aspect is the window's in fullscreen and 1 windowed. It is **opt-in per game**: the engine only widens the field when the game implements the optional `resize(width, height)`; games without it stay square. `GameContext.W` / `H` are properties of one mutable object, so a game must read `g.W` every time and never copy it. The engine applies the new aspect at the start of the next frame (`canvas.width` is set then; it clears the canvas, which the frame redraws) and tells React with `GameHandlers.field(width, height)`, which the engine calls (not the game). Asteroides: `resize` remaps `x` proportionally (`x' = x × w / W`, `y` unchanged), gives 1.5 s of invulnerability and keeps the run going; before its first `update` (a new game created before React sent the aspect) it regenerates the wave instead; a wave has `round((2 + level) × W / 480)` large rocks (5 at level 1 in 16:9, 3 windowed). Windowed and fullscreen scores are therefore not comparable: the real-scores spec must decide whether to store the mode.
  - Two directions only: canvas → React through `GameHandlers` (`score` / `lives` / `level` / `over`, called only when the value changes, so React does not render at 60 fps; plus the engine-driven `field`) and React → canvas through `RunningGame` (`setPaused`, `setScreenAspect`, `destroy`). The game owns its state; React owns pause, the game-over modal and saving. The P key and the PAUSA button are the app's; the game has no pause control.
  - `play-screen.tsx` starts the engine when loading ends (`loaded = phase !== "loading"`), destroys it on restart and unmount, and uses the real final score (`baseScore / 2` and "SIMULAR FIN DE PARTIDA" are only for games without an entry in `ARCADE_GAMES`).
  - Not done yet (future specs): touch controls (the mobile pad is still not wired to any game), a generic `CanvasGame` component, the other five games.
- `components/use-fullscreen.ts` (spec 08): `useFullscreen<T>()` returns `{ ref, supported, active, toggle }`. `play-screen.tsx` puts its whole `<main>` in fullscreen (so the game-over modal stays visible) but, while `active`, **only the canvas is shown**: no cabin frame, no React HUD, no PAUSA / SALIR bar, no touch pad, no vignette / scanlines and no "SIMULAR FIN DE PARTIDA"; the game's own HUD drawn inside the canvas stays. Enter with a "PANTALLA COMPLETA" button in the top bar next to PAUSA and SALIR, another one in the cabin's bottom row (between "ARCADE VAULT" and the red dot), or the **F** key (like **P**; ignored when held or with Ctrl / Meta / Alt). Leave with the "VENTANA" button over the bottom-right corner of the canvas (`aria-label="Salir de pantalla completa"`; bottom, because the canvas draws "NIVEL n" top-right), F, or Esc (native). Details that are easy to break:
  - `active` comes from `fullscreenchange`, never from the click. `supported` uses `useSyncExternalStore` (`false` on the server and while hydrating) so the button does not cause a hydration mismatch; with no `document.fullscreenEnabled` there is no button and F does nothing.
  - With `cacheComponents` Next keeps the previous route hidden (`display: none`) instead of unmounting it, and the browser does not leave fullscreen for a hidden element. The hook therefore calls `document.exitFullscreen()` in an effect cleanup when the screen is left (SALIR, VOLVER AL VAULT, back button).
  - Layout: windowed, the cabin width is `min(100%, 860px, calc(100svh - 170px))` (spec 07). - The magnet (spec 10) is a mouse-only easter egg that touches neither the engine nor the games (`lib/arcade/` is unchanged): `lib/magnet.ts` (constants, `MAGNET_PARAGRAPHS`, `MAGNET_SOURCES`), `components/magnet/` (`magnet-layer`, `magnet-halo`, `magnet-dialog`) and `public/cursors/iman.svg`. Full strength for 8 s and fade for the last 2 s; with `prefers-reduced-motion: reduce` (read live with `matchMedia`) there is no wobble, no time dependence and no fade: it just vanishes at 10 s. Non-default settings in `next.config.ts` that affect how code is written:

- **`cacheComponents: true`**: data fetching is dynamic by default. Opt into caching with the `use cache` directive (plus `cacheLife` / `cacheTag`). Routes prerender a static shell while dynamic content streams in, so uncached dynamic access (e.g. `cookies()`, `fetch`, `searchParams`) outside `<Suspense>` can fail the build. This requires the Node.js runtime, so do **not** export the `runtime` route segment config.
- **`partialPrefetching: true`**: by default `<Link>` prefetches only the route's App Shell. Use `<Link prefetch={true}>` to prefetch a link's URL-specific cached content.
- **`experimental.agentFeedback: true`**: lets `next dev` maintain agent instructions (the `AGENTS.md` block).
- **Tailwind CSS v4 via Turbopack**: wired through `turbopack.rules` using `@tailwindcss/turbopack` for `*.css`; there is no `postcss.config`. `app/globals.css` imports Tailwind with `@import "tailwindcss"` and exposes the theme via `@theme inline`: the old-TV palette `--color-crt-*` (spec 04), `font-pixel`, and animations like `animate-row-in`. There are no other color tokens (the neon `void` / `neon-*` / `ink-*` / `home-*` tokens and glow shadows were removed in spec 04).

Conventions:

- Breakpoints are done with Tailwind arbitrary variants, never `window.innerWidth`. The spec 01 screens (Library, detail, hall of fame, access, play) use a single breakpoint at 760 px (`min-[760px]:`). The header uses its reference's 840 px (`max-[841px]:` = ≤ 840). The landing keeps the breakpoints of its reference (features 4→2 cols at ≤980 and →1 at ≤520; game rail 6→3 at ≤1100 and →2 at ≤600; stats ≤720; activity/pricing ≤900; ticker rows ≤520), and so does "Acerca de" (highlights 3→1 at ≤820, contact 2→1 at ≤900). Tailwind v4's `max-[Npx]:` is `width < N` while the reference's `max-width: N` includes N, so they are written as N+1 (`max-[981px]:` ≡ `max-width: 980px`). Grids use plain `1fr` tracks (`grid-cols-[repeat(4,1fr)]`), not `grid-cols-4` (`minmax(0,1fr)`), because the reference lets wide content widen a column.

Body font stays Courier Prime (the reference's JetBrains Mono is not loaded).
